The Living Network

If two programs are running at the same time — how do they talk to each other?

How do two programs share information?

Each browser tab is its own little world. The code in Tab 1 can't reach into Tab 2 and grab a value. They don't have a phone line between them.

But they do share something: a small notebook that the browser keeps for each website. Any tab on the same site can read and write that notebook. Programmers call it localStorage.

The shared notebook

localStorage stores key-value pairs — like a dictionary, or a list of labeled jars. You store something by giving it a name, and you get it back by asking for that name.

// Tab 1 (Star) writes a letter: localStorage.setItem("star_to_ivy", "Hello Ivy!"); // Tab 2 (Ivy) reads it: localStorage.getItem("star_to_ivy"); // → "Hello Ivy!"

Star never directly called Ivy. Ivy never asked Star to send anything. They both just know where to look — a name they agreed on in advance.

This pattern — write to a shared location, poll to see what's there — is how a huge amount of real-world software works. Databases, message queues, shared files. The notebook is small; the concept is everywhere.

The overwrite problem

There's a catch. localStorage only holds one value per key. If Star sends two letters in a row, the second one replaces the first.

localStorage.setItem("star_to_ivy", "Hi!"); // ✓ stored localStorage.setItem("star_to_ivy", "Oops, again!"); // overwrites localStorage.setItem("star_to_ivy", "Third one!"); // overwrites again // Ivy checks: localStorage.getItem("star_to_ivy"); // → "Third one!" — first two are gone

Ivy only ever sees the last thing Star wrote. This is a real bug — and it's the kind of bug that's invisible unless you think carefully about timing.

The timestamp fix

The solution: store a timestamp alongside the message. Ivy remembers the timestamp of the last letter she already read. If the new letter has a newer timestamp — it's new. If it's the same or older — she's already seen it.

// Star sends a letter with a timestamp: let letter = { text: "Hi Ivy!", time: Date.now() }; localStorage.setItem("star_to_ivy", JSON.stringify(letter)); // Ivy checks — did I already read this one? let lastSeen = parseInt(localStorage.getItem("ivy_last_star_ts") || 0); let msg = JSON.parse(localStorage.getItem("star_to_ivy")); if (msg && msg.time > lastSeen) { // New letter! Show it. localStorage.setItem("ivy_last_star_ts", msg.time); // mark as read }
Date.now() returns a number that goes up every millisecond — the number of milliseconds since January 1, 1970. Every call to Date.now() returns a bigger number than the last one. That's what makes it a reliable timestamp.

What this looks like in the notebook

After Star sends a letter and Ivy reads it, the shared notebook looks like this:

star_to_ivy → {"text":"Hi Ivy!","time":1749123456789} ivy_last_star_ts → 1749123456789

The first key is the letter. The second key is Ivy's "I already read this" marker. Both live in the same shared notebook. Neither pet deletes the other's entries — they just know which keys belong to them.

Something to think about: What if both pets write to each other at exactly the same millisecond? What if Star closes the tab while Ivy is mid-read? These edge cases are real problems in production systems — and they're also why engineers think carefully about timing before they ship.

The network grows

With 4 pets, there are 12 routes: A→B, A→C, A→D, B→A, B→C, B→D, and so on. Each route is one localStorage key. The pets don't need to know about each other's routes — they just need to know their own keys.

That structure — many small independent channels, each with a known name — is how real messaging systems are designed at much larger scale.
