If you have four programs, how do you put them all on one screen?

Imagine four pet games — Star the axolotl, Ivy the owl, Astro the cat, and Gerald the rotisserie chicken — each living in its own separate HTML file. They work great on their own. Now someone asks: can we show all four at once, in a grid, like a TV split-screen?

That's exactly what a dashboard does.

What is a dashboard?

A dashboard is a page whose job is to show other pages, not to be a page itself. You see dashboards everywhere: a flight display at the airport shows multiple gate statuses; a stock ticker shows many symbols at once; a classroom hub might show the weather, the schedule, and a live camera feed.

Dashboards exist for one reason: it's much easier to build four small focused programs and then compose them into one view than to build one giant program that does everything.

The iframe element

HTML has a built-in way to embed one page inside another: the iframe (inline frame). You give it a src attribute pointing to any URL, and the browser loads that page inside a rectangle on your page.

<iframe src="star/index.html" width="700" height="500" title="Star the Axolotl" ></iframe>

The critical thing to understand: the inner page has no idea it's inside an iframe. It runs completely independently. Its JavaScript, its animations, its timers — all isolated. This is intentional.

Security feature: The inner pages don't know they're in a grid. iframes are intentionally isolated — that's a browser security feature, and it's exactly why the hub works without modifying the pets. Each pet just runs normally. The hub arranges them.

CSS Grid: arranging the cells

To place four iframes in a 2×2 grid, we use CSS Grid. Grid lets you divide a container into rows and columns, then place children into those slots automatically.

/* The outer page layout */ body { margin: 0; background: #111; } .grid { display: grid; grid-template-columns: 1fr 1fr; /* 2 equal columns */ grid-template-rows: 1fr 1fr; /* 2 equal rows */ gap: 8px; width: 100vw; height: 100vh; } .cell { position: relative; overflow: hidden; cursor: pointer; } .cell iframe { border: none; width: 700px; /* the pet's native width */ height: 500px; /* the pet's native height */ pointer-events: none; /* let clicks pass to the cell */ transform-origin: top left; }

The 1fr unit means "one fraction of the available space." Two columns of 1fr 1fr each get exactly half the width. Add more fractions and they divide proportionally.

The scaling trick

Here's the problem: each pet page is designed to run at 700px wide. But the grid cells might only be 400px wide — less than half the screen. If you load the iframe at 700px, it overflows its cell.

The fix: keep the iframe at its native size, and use a CSS transform: scale() to shrink it visually. The math is simple:

function scaleFrames() { const cells = document.querySelectorAll('.cell'); cells.forEach(cell => { const cellW = cell.clientWidth; // actual rendered width const cellH = cell.clientHeight; // actual rendered height const sx = cellW / 700; // how much to shrink horizontally const sy = cellH / 500; // how much to shrink vertically const frame = cell.querySelector('iframe'); frame.style.transform = `scale(${sx}, ${sy})`; }); } window.addEventListener('resize', scaleFrames); scaleFrames(); // run once on load too

If the cell is 350px wide and the iframe is 700px wide, then sx = 350 / 700 = 0.5. The iframe gets scaled to exactly fit.

Why pointer-events: none?

By default, an iframe captures all mouse events — clicks, hovers, everything. That's great when you want to interact with the pet. But in the hub, you want clicking a cell to expand it, not interact with the pet inside.

Setting pointer-events: none on the iframe makes it invisible to mouse events. Clicks fall through to the parent .cell div, which runs your expand function.

The close button placement problem

When a cell expands into an overlay, you need a close button. The obvious place to put it: right on top of the overlay. But there's a trap.

If the close button is positioned over the iframe — even if it looks like it's "on top" visually — the iframe will intercept the click. iframes own every pixel of their rectangle, even through CSS layers.

The rule: The close button must live outside the iframe's area in the parent document, or the iframe will intercept the click and it'll never fire. Use position: fixed on the button and place it in a corner of the viewport, not inside the overlay box. Fixed-position elements live in the viewport layer, above all iframe areas.

Expand and collapse

When a cell is clicked, the hub shows an overlay with the pet at full size. Here's the pattern:

let activeCell = null; function expandCell(cell) { activeCell = cell; const src = cell.dataset.src; const overlay = document.getElementById('overlay'); const frame = document.getElementById('overlay-frame'); frame.src = src; // load the pet in the big iframe overlay.classList.add('open'); document.getElementById('close-btn').classList.add('open'); } function collapseOverlay() { document.getElementById('overlay').classList.remove('open'); document.getElementById('close-btn').classList.remove('open'); document.getElementById('overlay-frame').src = ''; // free memory activeCell = null; }

Note that the close button element is placed directly on the <body> — not inside the overlay div. position: fixed; top: 16px; right: 20px puts it in the viewport's top-right corner, safely outside every iframe's rectangle.
